# 最终文本审读与退稿

程序只核对审稿输入、覆盖、证据和版本；创作判断由实际阅读的编审完成。先读正文，再看作者资料。不可把现成预期答案或旧评分塞给首读者。已见预期的回放标 `knowledgeOfExpectations: informed`，不得冒称盲评。

## 两遍阅读

运行 `workflow.py PROJECT review-pack --stage final --episodes 1-30 --front-matter PROJECT/front-matter.md`。初读包仅含按顺序的正文，每块默认400行并带前20行衔接。可调 `--chunk-lines`，不得用摘要替代缺失原场。逐块读，保存主人公此时要做什么、担心什么、哪件事迫使其换做法、哪些已明说/只能猜、第一次看不懂的位置及原文证据。读完复述主要因果。

`first-read` 提交实际读过的有序 chunk IDs 和每块读者笔记；未读完就是 `reading_incomplete`，中断后继续同一会话。提交笔记后 `reveal-context` 才装配已确认底稿、大纲、来源、钱物流转和人物/知情/道具/伏笔账本。对照复读实际场次，核对首读卡点，不倒填“首读已理解”。

`record-review` 的覆盖必须与该次所有集、场、正文哈希及行数一致。按因果、动机、知情、连续性、伏笔、节奏、声纹、题材、前置模块与来源保真分别给结论、原因、原文证据。所有到期与未来伏笔按账本逐项列 setup/payoff 证据；部分交付可标未来区间与负责人，全剧终不能用未来搪塞。反向从结局证据回查取得与持有人。账款核付款人、收款人、条件和责任，不只加总。静场、克制对白、反复物件若改变关系或理解应保留。

## 问题与放行

问题含稳定 ID、P0–P3、类别、集场、实际引文、读者为何卡住、影响集、退回阶段、修法与复检范围。明确矛盾、缺交代和个人审美分别说明。核心因果无法复述、关键选择无先决条件、提前知情、到期主线未回收等阻断。风格偏好可作 P2/P3。固定问题不能仅手改状态：修复必须重新提交当前文本的会话、复检前因和后果并留下原文证据。P1 的创作取舍仅在非硬事实类别且有用户原话/消息定位时可接受；不能接受锁定事实、角色知情、道具、时间线、主线因果或到期伏笔错误。

批次审稿用相同命令的 `--stage batch`；其作用是及时返修，不替代最终连续通读。每个问题最多两轮自动返修，仍不通过保留待修稿、争议原场及取舍交用户；审稿任务只诊断，生产任务在已授权范围内修。结构返修回底稿/大纲，改动核心大纲后重新取得确认。局部语言问题再交润色。

正文、依赖、账本或前置材料变化会使该次审核不可复用，旧会话留作历史。`workflow.py PROJECT status` 在断点恢复时持久化失效；`check-writing/check-release` 和批准/正式导出都即时比哈希，手填 `openBlockingIssues: 0` 不能绕过。最终经当前正文通读、局部润色语义核对及完整前置审查，先暂存 Word、抽取可见文本核对、逐页实物验收，通过后发布到交付目录。低层版式函数只生成明显预览。

## 方法使用记录

每个阶段记录真正改变的决定及证据：`capabilityId, decisionId, upstreamDecisionId, action, changedDecision, evidence`。没有适用方法时记录具体跳过原因。通常每项子任务取《故事》1张，跨领域至多2张，阶段可更换。编审追查一个大纲取舍如何变成分集的后果、场次策略和能演的台词；演员版不显示卡号。检索命中或填写表格本身不算使用。
